### **Deliverable 5: Viva (Oral Examination)**

**Key topics to be ready to discuss:**

#### 1. **Architecture & Design**
- Explain producer-consumer pattern
- Why Kafka topics (4 separate ones for different metrics)
- Role of each machine
- How windowing helps detect anomalies

**Sample Q: "Why 4 separate Kafka topics instead of 1?"**
- A: Each topic serves a specific purpose. topic-cpu/mem go to Consumer 1 for CPU+Memory analysis. topic-net/disk go to Consumer 2 for network analysis. This separation allows parallel independent processing.

#### 2. **Implementation Details**
- Window size: 30 seconds
- Slide interval: 10 seconds
- Why these specific values
- Computation per server
- Aggregation methods (AVG vs MAX)

**Sample Q: "Why use AVG for CPU but MAX for Network?"**
- A: AVG (average) for CPU/Memory shows sustained load. MAX (maximum) for Network/Disk captures peak traffic/load events which are more important for anomaly detection.

#### 3. **Data Processing Math**
- 28,800 input rows (why this number)
- How it becomes 14,400 output rows
- Calculation: 28,800 records ÷ 2 (merge CPU+Mem) = 14,400 base
- But actually: 20 servers × 720 time windows × 1 row per server per window = 14,400

**Sample Q: "How many servers and time windows?"**
- A: 20 unique servers (server_1 through server_20). With 30-second windows sliding every 10 seconds over ~2 hours of data, we get 720 windows. So 20 servers × 720 windows = 14,400 rows.

#### 4. **Alerting Logic**
- CPU+Memory thresholds
- Network+Disk thresholds
- Alert conditions (AND logic)
- Your specific thresholds from thresholds.txt

**Sample Q: "What alert appears when both CPU AND Memory are above threshold?"**
- A: "High CPU + Memory stress" - indicates the server is under heavy load in both metrics simultaneously.

#### 5. **Troubleshooting & Edge Cases**
- How would you debug if output was wrong?
- How to verify window boundaries are correct?
- How to check if data is sorted properly?
- What if values don't match expected?

**Sample Q: "Your output shows 2182 mismatches. What could cause this?"**
- A: Likely rounding precision issues. Python uses banker's rounding while expected output might use standard rounding. Or window boundary issues (inclusive vs exclusive). I'd check: (1) rounding method, (2) window boundaries, (3) data sorting, (4) aggregation logic.

#### 6. **Scaling & Real-World Application**
- How would this work with real Kafka?
- What if you had 1000 servers instead of 20?
- How would ZeroTier help in distributed environment?

**Sample Q: "What changes if this runs on real Kafka vs your simulation?"**
- A: The data processing logic stays identical. Instead of simulating topics in memory, real Kafka would persist messages and consumers would pull from brokers. ZeroTier ensures machines can communicate securely. The window aggregation and alert logic would be unchanged.
